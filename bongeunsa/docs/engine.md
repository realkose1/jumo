# 공통 엔진 설계

세 공간은 같은 엔진을 쓰고, 공간마다 다른 것은 '공간 정의' 하나로 갈아 끼운다. 엔진에 공간 이름이 하드코딩되면 안 된다.

## 1. 공간 정의 (SpaceDefinition)

공간마다 `src/spaces/<id>/index.ts`에서 이 모양의 객체를 내보낸다. 아래는 방향을 보여주는 초안이고, 만들면서 다듬는다.

```ts
interface WordList { adjectives: string[]; nouns: string[] }
// 화면(UI) 모양. 모두 선택 항목이고 없으면 밝은 기본값. 키 하나가 CSS 변수 하나(accent -> --qs-accent)
interface SpaceUiTheme {
  accent?: string; accentInk?: string;                    // 강조색과 그 위의 글자색
  surface?: string; surfaceSolid?: string; surfaceStrong?: string; // 반투명 면, 블러 없는 곳의 면, 설정 창 면
  ink?: string; inkSoft?: string; line?: string;          // 글자, 보조 글자, 선
  radius?: string; blur?: string;                         // 모서리 둥글기, 배경 블러 세기
}

interface SpaceDefinition {
  id: string;                     // 예: 'reading-room', 'laundromat', 'palace-pond', 1단계 시험용 'test-room'. 엔진에 공간 이름을 하드코딩하지 않는다
  title: { ko: string; en?: string };
  capacityPerRoom: number;        // 방 하나 정원. 기본 50, 공간마다 다를 수 있다(빨래방 16명)
  initialRoomCount: number;       // 시작 방 개수. 기본 10, 공간마다 다를 수 있다(빨래방 30개). 서버 설정으로 늘릴 수 있게
  nameWords: { ko: WordList; en?: WordList }; // 언어별 자동 이름 단어. 영어를 함께 제공하는 공간(고궁)만 en을 둔다
  avatarOutfit: string;           // 공통 캐릭터에 입힐 옷
  seats: SeatDef[];               // 1인 1석 자리 목록
  actions: [ActionDef, ActionDef, ActionDef]; // 1, 2, 3 키. ActionDef의 notice는 인사 알림 뒷말('폴짝 인사했어요'), 없으면 이름표+'했어요'
  greetingActionId: string;       // 셋 중 '말 없는 인사'
  sound: SoundLayers;             // 환경음, 공동 소리, 효과음
  schedule: ScheduleEvent[];      // 한국 시간 기준 공동 순간
  personalCounters: CounterDef[]; // 나에게만 보이는 누적
  loadingToy: LoadingToyDef;      // 로딩 중 손장난
  donation: { label: string; url?: string }; // 후원 버튼 문구
  theme?: SpaceUiTheme;           // 선택. 화면(UI)의 강조색 등. --qs-* 변수로 들어간다(docs/design.md)
  loadScene(ctx: SceneContext): Promise<SceneHandle>;
}
```

## 2. 엔진이 책임지는 것

### 입장
- 주소에서 공간과 방을 읽는다. 방 번호가 없으면 사람이 적당히 있는 방에 자동 배정한다(텅 빈 방보다 몇 명 있는 방이 낫다).
- 방 목록 창: 방마다 현재 인원을 보여주고 골라서 옮길 수 있다.
- 방이 차면 "이 방은 지금 자리가 다 찼어요" 안내와 함께 다른 방을 추천한다.

### 캐릭터
- 공통 캐릭터 하나(둥근 머리의 작은 사람)에 공간별 옷만 바꿔 입힌다.
  - 열람실: 카디건과 안경
  - 빨래방: 잠옷과 슬리퍼
  - 고궁: 소풍 한복
- 옷은 색과 작은 소품으로 표현한다(도형으로 만든 안경, 슬리퍼, 한복 저고리 색 등).
- 캐릭터는 반드시 직접 만든 원본이어야 한다. 알려진 캐릭터를 닮게 만들지 않는다.
- 캐릭터는 기본 도형(구, 캡슐 등)을 코드로 조합해 만든다. 외부 3D 파일은 쓰지 않는다.
- 내 캐릭터는 고해상도, 다른 사람 캐릭터는 저해상도 버전을 쓴다. 해상도 차이는 도형의 분할 수로 조절하고, 같은 해상도의 캐릭터는 인스턴싱으로 한 번에 그리는 방식을 유지한다.

### 이동과 시점
- 바닥을 누르면 그곳까지 걸어간다. WASD와 방향키도 된다.
- 드래그로 둘러보고, 휠이나 두 손가락으로 확대와 축소를 한다.
- 3인칭 뒤에서 보는 시점이 기본이다.
- 자리를 누르면 걸어가서 앉는다. 다른 사람이 앉은 자리는 앉을 수 없다(서버가 판정).

### 동작 세 개
- 화면 아래 버튼 세 개, 숫자키 1, 2, 3.
- 동작은 서버를 거쳐 같은 방 모두에게 보인다.
- 인사 동작은 가까운 사람(또는 지정한 사람)에게 "OO님이 ~했어요" 알림 한 줄을 띄운다.
- 같은 동작 연타는 1초에 1번으로 제한한다.

### 소리 세 층
- 환경음, 공동 소리, 효과음을 따로 켜고 끄고 크기를 조절한다.
- 처음에는 소리가 꺼진 상태로 시작하고, 사용자가 화면을 한 번 누른 뒤 켤 수 있다(브라우저 자동 재생 규칙).
- 다른 탭으로 가면 소리를 멈추는 것이 기본이고, 설정에서 계속 듣기를 고를 수 있다.

### 시간 시스템
- 모든 공동 일정은 한국 시간(Asia/Seoul) 기준이다.
- 접속할 때 서버 시각을 받아 기기 시계와의 차이를 보정한다. 그래야 모든 사람이 같은 순간에 종소리를 듣는다.
- 일출, 일몰은 서울 좌표로 계산한다(외부 API 없이 계산식으로).
- 날씨 연동(비 오는 날 등)은 2차 버전에서 기상청 자료로 붙인다.

### 개인 기록
- 1차 버전은 기기 저장소에만 저장한다. 키는 `bongeunsa:<공간id>:<항목>`.
- 저장소가 막혀 있어도(사생활 보호 모드 등) 화면은 정상 동작해야 한다.
- 개인 기록은 서버로 보내지 않는다.

### 로딩
- 로딩 화면에는 공간별 '손장난'을 둔다(열람실: 연필 돌리기, 빨래방: 동전 넣기, 고궁: 연못 물결).
- 3D 장면을 먼저 흐리게 깔고, 준비되면 걷어낸다. 로딩 화면 바탕은 밝은 크림색이다(`docs/design.md`).

### 설정 창
- 소리 세 층 조절
- 자료 정보: `credits.json`을 읽어 모든 자산의 출처와 라이선스를 보여준다
- 조작 방법 안내
- 움직임 줄이기: 기기의 '동작 줄이기' 설정을 존중하고, 카메라 흔들림이나 큰 애니메이션을 줄인다

## 3. 실시간 서버 (server)

Cloudflare Worker 하나와 Durable Object. 방 하나 = 객체 하나 (`<공간id>:<방번호>`, 방 번호는 1부터). 공간별로 '로비' 객체(`lobby:<공간id>`)가 하나 더 있어서 방별 인원과 하루 선물 횟수를 모은다. 모두 SQLite 기반 Durable Object이고, WebSocket 휴면(Hibernation) 방식을 써서 조용히 앉아 있는 동안에는 객체가 메모리에서 내려간다. 연결별 상태(번호, 이름, 위치, 자리, 상태 값)는 연결에 붙인 attachment에 두고, 깨어날 때 다시 모은다.

### 공유 폴더 (shared/)
화면과 서버가 같은 값을 보도록 저장소 루트의 `shared/`에 둔다. 3D와 소리와 화면 문구는 넣지 않는다.
- `shared/protocol.ts`: 아래 메시지 규약의 타입, 연결 닫기 코드(`CLOSE`), 제한값(`LIMITS`)
- `shared/spaces/<id>.ts`: 서버도 알아야 하는 공간 데이터. 공간 id, 정원, 시작 방 개수, 이름 단어(언어별), 자리 id 목록, 동작(id, 인사 여부, 선물 여부와 하루 제한), 사람별 상태 키(스탠드 켬 등)
- `shared/spaces/index.ts`: id로 찾는 목록
- 화면의 `SpaceDefinition`(`web/src/spaces/<id>`)과 겹치는 값(정원, 자리 id, 동작 id, 이름 단어)은 `shared/`가 원본이다. 자리 id는 아직 임시 규칙이라 장면을 만들 때 확정한다.

### 화면 쪽 연결 (web/src/engine/net/)
- `PresenceClient`: WebSocket 연결, join, 재접속(지수 백오프 1초에서 30초까지, 탭이 숨겨져 있으면 30초 이상), 글자 `ping` 연결 유지, 서버 시각 보정. 서버 주소는 `VITE_PRESENCE_URL`(개발은 `.env.development`의 `ws://localhost:8797`, 비어 있으면 혼자 모드).
- `session.ts`(NetSession): 연결, 다른 사람 그리기(`engine/RemotePeers.ts`, InstancedMesh), 서버 판정 자리(`PresenceSeatArbiter`), 내 위치 보내기(`moveSender.ts`: 바뀌었을 때만 초당 10번 이하)를 묶는다. 서버가 없거나 끊기면 로컬 자리 판정으로 돌아간다.
- 앉기 순서: 마지막 위치를 먼저 보내고 `sit`을 보낸다. 서버가 앉은 채 `move`를 받으면 일어난 것으로 보므로, 앉았거나 답을 기다리는 동안에는 `move`를 보내지 않는다.
- 이름표: 평소에는 없다. 마우스를 올리거나 누르면 그 사람 머리 위에 잠깐 보인다(`engine/peerLabel.ts`와 `ui/net.ts`).
- 정원, 이름 단어, 자리 id, 동작 id는 `@shared/spaces`(저장소 루트 `shared/`)가 원본이고 각 공간 모듈이 읽어 쓴다. `src/spaces/shared.test.ts`가 서버와 화면의 id가 같은지 확인한다.

### 접속 주소와 순서
- `GET /ws?space=<공간id>&room=<방번호>` 로 WebSocket을 연다. `room`을 빼면 서버가 사람이 적당히 있는 방을 골라 주고, 어느 방인지는 `welcome.room`에 담아 보낸다.
- 연결하면 5초 안에 `join`을 보낸다. 서버는 `welcome`으로 답한다. 정원이 찼으면 `room-full`을 보내고 닫는다.
- `GET /rooms?space=<공간id>` 로 방별 인원과 추천 방을 받는다. `GET /health` 는 상태 확인.
- 연결이 끊기면 같은 순서로 다시 연결한다. 서버는 끊긴 사람을 바로 방에서 빼고(자리도 풀린다), 다시 들어오면 새 번호와 새 이름을 준다.

### 서버가 결정하는 것
- 정원 초과 여부. 넘으면 추천 방과 함께 `room-full`
- 이름 배정: 공간 단어 목록에서 '형용사 명사'로만 뽑고, 같은 방 안에서 겹치지 않게 한다. 단어 조합이 모자라면 뒤에 숫자를 붙인다. 영어를 함께 제공하는 공간은 한국어와 영어를 한 쌍으로 뽑되 두 언어 모두 겹치지 않게 한다(영어는 단어 첫 글자를 대문자로 보낸다).
- 자리 점유(1인 1석, 먼저 온 사람). 같은 자리에 동시에 앉으면 먼저 처리된 한 명만 성공하고 나머지는 `seat-taken`. 일어나거나, 앉은 채 움직이거나, 나가면 풀린다.
- 인사 동작의 받는 사람: 지정하지 않으면 마지막 위치가 가장 가까운 사람(같은 거리면 번호가 작은 사람)
- 선물 동작의 하루 제한: 기기 식별값별로 한국 시간 자정 기준. 방이 아니라 공간 단위로 세서 방을 옮겨도 이어진다(로비 객체의 저장소).
- 동작과 이동의 속도 제한, 서버 시각
- 공간별 점유물(세탁기 등)은 연결이 끊긴 뒤 유예 시간(빨래방 5분) 뒤에 해제한다. 이 부분은 빨래방 단계에서 만든다(지금은 사람별 상태 값 `washer`만 전달한다).

### 메시지 규약 (JSON, 짧게)

모든 메시지는 JSON 텍스트 한 덩어리이고 `t` 필드로 종류를 가른다. 타입 정의는 `shared/protocol.ts`가 원본이다. 사람은 방 안에서 서버가 붙이는 정수 번호(`id`)로 가리킨다.

클라이언트가 보내는 것
| 종류 | 필드 | 내용 |
|---|---|---|
| `join` | `space`, `room?`, `dev`, `x?`, `z?`, `r?` | 연결 뒤 첫 메시지. 공간 id, 방 번호, 기기 식별값(8~64자, 영문 숫자 - _, 기기에 한 번 무작위로 만들어 저장), 처음 서 있는 곳 |
| `move` | `x`, `z`, `r` | 위치와 바라보는 방향. 움직일 때만, 초당 최대 10번 |
| `sit` | `seat` | 자리 id |
| `stand` | 없음 | 일어난다 |
| `act` | `act`, `to?` | 동작 id, 인사 받을 사람(선택). 같은 동작은 1초에 한 번 |
| `state` | `key`, `val` | 공간별 상태 변화(스탠드 켬 등). 키와 값 범위는 공간 데이터가 정한다. 초당 최대 2번 |
| `ping` | `c?` | 연결 확인. 보낸 시각 `c`를 `pong`에 그대로 돌려준다 |

서버가 보내는 것
| 종류 | 필드 | 내용 |
|---|---|---|
| `welcome` | `id`, `name`, `space`, `room`, `capacity`, `peers`, `seats`, `now`, `limits` | 내 번호와 이름(언어별), 나를 뺀 지금 사람들(이름은 언어별, 위치, 상태 값), 자리 점유 현황(자리 id에서 사람 번호로), 서버 시각(ms), 제한값 |
| `peer-join` / `peer-leave` | `peer` / `id` | 들어오고 나간 사람 |
| `peer-move` | `now`, `p` | 위치 묶음 `[번호, x, z, r]`의 배열. 움직인 사람들을 모아 초당 약 8번. 움직임이 없으면 오지 않고, 혼자 움직인 사람에게는 자기 위치를 돌려보내지 않는다 |
| `seat` | `seat`, `id` | 자리 점유(`id`가 번호)와 해제(`id`가 null) |
| `act` | `id`, `act`, `to?`, `left?` | 누가 무슨 동작을 했는지. 보낸 사람에게도 돌아오고, 선물 동작이면 보낸 사람 것에만 오늘 남은 횟수 `left`가 붙는다 |
| `notice` | `kind`, `from`, `name`, `act` | 인사 알림(받는 사람에게만). 문장("OO님이 ~했어요")은 화면이 만든다 |
| `state` | `id`, `key`, `val` | 다른 사람의 상태 값이 바뀌었다 |
| `room-full` | `rec` | 정원 초과. 추천 방 번호(없으면 null). 이 뒤에 서버가 연결을 닫는다 |
| `pong` | `c?`, `now` | `ping`의 답. 서버 시각(ms) |
| `error` | `code`, `ref?` | `bad-request`, `rate-limited`, `seat-taken`, `daily-limit`, `no-target`. 연결은 유지된다 |

연결 닫기 코드(WebSocket close code): 4001 같은 기기가 같은 방에 다시 들어와서 이전 연결을 닫음, 4002 정원 초과, 4003 같은 IP 연결 초과, 4004 첫 `join`이 없거나 틀림, 4005 잘못되거나 너무 잦은 메시지가 계속됨.

- 사용자가 쓴 글자가 오가는 필드는 없다. 문자열은 모두 공간 데이터에 있는 id와 대조하고, 이름은 서버가 붙인다.
- 문자 `ping`을 보내면 서버가 객체를 깨우지 않고 `pong`으로 답한다. 연결을 유지하는 용도로 쓰고, 서버 시각이 필요하면 JSON `ping`을 쓴다.
- 서버 시각 보정: JSON `ping`의 `c`에 기기 시각을 담아 보내고 `pong`을 받으면 `왕복 = 지금 - c`, `차이 = pong.now + 왕복 / 2 - 지금`으로 구한다. 처음 접속할 때 `welcome.now`로 먼저 맞추고, 몇 번 재서 왕복이 가장 짧았을 때의 차이를 쓴다.

### 알람
- 방 객체의 알람은 로비 인원 알림(`due:report`) 하나에만 쓴다. 다음 알림 시각은 저장소에 두어 휴면이나 재시작 뒤에도 이어진다.

### 방 현황과 추천
- `GET /rooms?space=<공간id>` → `{ space, capacity, rooms: [{ room, n }], recommended, now }`. `Cache-Control: public, max-age=3`이고 Worker 안에서도 몇 초(`ROOMS_CACHE_MS`) 들고 있는다.
- 방 객체는 인원이 바뀔 때 로비 객체에 알린다. 2초 안에 또 바뀌면 묶어서 한 번만 보내고, 사람이 있는 동안은 10분마다 다시 알린다. 로비는 25분 넘게 소식이 없는 방을 빈 방으로 본다.
- 추천 방: 정원의 60% 이하이면서 1명 이상인 방 가운데 가장 많은 방. 없으면 정원이 안 찬 방 가운데 가장 한산한 방. 같으면 번호가 작은 방. 갈 곳이 없으면 null.
- 방 개수와 정원은 `shared/spaces`의 기본값이고, 서버 설정 `SPACE_OVERRIDES`(JSON)로 공간별로 덮어쓴다. 예: `{"laundromat":{"rooms":60}}`. (산사는 정원 20명으로 시작했다가 접속이 몰려 서버가 멈췄고, 급히 방당 100명, 방 100개로 늘렸다.)

### 악용 방지
- 글자 입력이 없으니 신고 기능은 1차에서 만들지 않는다.
- 같은 기기 식별값이 같은 방에 다시 들어오면 새 연결을 받고 이전 연결을 닫는다(코드 4001). 새로고침이나 재접속 때 옛 연결이 남아 있어도 막히지 않게 하려는 선택이다.
- 같은 IP(`CF-Connecting-IP`)가 한 방에 동시에 여는 연결 수는 `MAX_CONN_PER_IP`(기본 6)까지. 사무실이나 PC방처럼 한 IP를 여럿이 쓰는 곳이 있어서 설정으로 바꿀 수 있게 했다.
- 속도 제한은 연결마다 1초 단위로 센다: `move` 10, `state` 2, `sit`과 `stand` 합쳐 4, `act` 합쳐 6(같은 동작은 1초 1번), 모든 메시지 합쳐 40. 넘친 메시지는 버리고 `rate-limited`로 알린다(`move`는 말없이 버린다). 틀린 메시지나 버려진 메시지가 계속 쏟아지면 연결을 닫는다.
- 메시지는 512자까지, 좌표는 절댓값 500까지. 모양이 틀린 것은 무시한다.
- 웹소켓 접속을 허용할 Origin은 `ALLOWED_ORIGINS`로 제한할 수 있다(비우면 모두 허용, 배포 때 채운다).
- 하루에 보낼 수 있는 선물(귤, 요구르트, 잉어 먹이) 수를 기기 식별값별로 제한한다. 인사를 겸하는 선물은 받을 사람이 있을 때만 하나를 쓴다. 기기 식별값은 기기에서 지우면 새로 만들어지는 값이라 완전한 막이 아니라 스팸을 줄이는 장치다.

### 로컬 실행
- `server`에서 `npm run dev` (wrangler dev, 로컬 모드, 포트 8797). 계정이 필요 없다.
- `npm test`는 Durable Object까지 실제로 돌리는 시험(vitest-pool-workers), `npm run typecheck`은 타입 검사. 서버 규칙(변형, 다시 하기 간격, 선물, 상태, 이름 목록, 방 더 열기)은 시험 전용 공간(`server/test/fixtures.ts`의 `fixture`)으로 확인하고, `test/setup.ts`가 이 공간을 `SHARED_SPACES`에 넣는다.

## 4. 성능 예산

| 항목 | 목표 |
|---|---|
| 첫 로딩 용량 | 8MB 이하(가능하면 5MB) |
| 첫 화면까지 | 휴대폰 4G 기준 4초 이내 |
| 그리기 호출 수 | 150 이하 |
| 삼각형 수 | 휴대폰 30만 이하 |
| 화면 갱신 | 컴퓨터 60fps, 휴대폰 최소 30fps |

- 성능이 낮은 기기는 그림자와 후처리 효과를 자동으로 끈다.
- 탭이 숨겨지면 그리기를 멈춘다.
- 화면 밖 사람의 애니메이션은 갱신하지 않는다.
- 첫 장면에 필요 없는 자산은 늦게 불러온다.

## 5. 측정

- 개인정보 없는 방문 통계만(Cloudflare Web Analytics 정도).
- 공간별로 셀 것: 입장, 머문 시간, 동작별 횟수, 공동 순간 전후 동시접속.

## 6. 배포

- 정적 화면과 실시간 서버를 모두 Cloudflare에 둔다.
- 주소 구조: 공간 고르는 첫 화면은 만들지 않고, 세 공간을 각자 따로 링크로 공개한다. 경로(`/reading-room` 등)로 둘지 공간별 도메인으로 둘지는 5단계(열람실 먼저 공개)에서 정한다. 공통 엔진 구조는 그대로이고, 앱을 세 개로 나누는 것은 아니다.
- 계정, 도메인, 결제가 필요한 단계에서는 사용자에게 먼저 묻는다.
